# T12: roles de la base y respaldo fuera del contenedor

## Qué se hace
- **Roles** (`scripts/roles.sql` + `scripts/roles.ts`, idempotente, corre después de las migraciones en el servicio
  `migrar`):
  - `btw` (dueño, ya existe): migraciones;
  - `btw_app`: SELECT, INSERT, UPDATE en todas las tablas de `public`; DELETE solo en `sesion`, `desafio` e
    `invitacion` (si existen); sin DDL; uso de secuencias; privilegios por defecto para tablas futuras;
  - `btw_lectura`: solo SELECT.
  - Contraseñas desde variables (`POSTGRES_APP_PASSWORD`, `POSTGRES_LECTURA_PASSWORD`), nunca impresas ni en git.
- **Compose de producción:** `app` y `cron`→`app` usan `btw_app`; `migrar` corre migraciones + roles como dueño.
  `app` recibe además `WEBAUTHN_RP_ID`, `WEBAUTHN_ORIGEN` y `WEBAUTHN_RP_NOMBRE`.
- **Respaldo:** además del volumen, copia cada respaldo a una carpeta del host (`RESPALDO_HOST_DIR`, bind mount;
  por defecto `./respaldos/produccion`), con la misma retención.
- **Restauración probada** en una base aparte (script `docker/respaldo/probar-restauracion.sh` o prueba).

## Criterios de aceptación
1. Prueba de base (rojo primero): con `btw_app`, INSERT/UPDATE/SELECT funcionan, DELETE en `reel` falla, CREATE
   TABLE falla; `btw_lectura` no puede INSERT. Correr `roles` dos veces no falla.
2. Un respaldo real queda en el volumen y en la carpeta del host; se restaura en una base aparte con los mismos
   conteos.
3. `npm run verificar` en verde; `docker compose -f docker-compose.prod.yml config` válido.
